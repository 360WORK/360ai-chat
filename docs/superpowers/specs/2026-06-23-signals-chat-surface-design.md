# Signals → chat.360ai Surface — Design Spec

Sub-project of the AI Acumen / 360AI-chat arc. Date: 2026-06-23.

## 1. Summary

Surface recruiter **Signal digests** (generated by the Laravel Signals engine) inside
**chat.360ai** (this LibreChat fork), in a dedicated per-user "Signals" conversation, as
assistant messages. The Laravel engine already exists and is ~95% built but dormant
(`signals:tick` is commented out) and its only existing consumer is the **agent.360ai**
chat app (Laravel+Inertia). The product has since consolidated chat into **chat.360ai**;
this spec delivers Signals to the current chat surface.

## 2. Context / reality (from investigation 2026-06-23)

- **Laravel side (`/Users/eth0/Herd/360ai`, branch `feature/360ai-chat-auth`):** full stack
  present — `signals`/`signal_runs`/`signal_subscriptions` tables, models, Internal API
  (`Api/Internal/{SignalsController,SignalRunsController}`) gated by
  `auth:sanctum`+`web` (SESSION-cookie auth — for agent.360ai's browser only), a strategy
  engine (`StrategyResolver`/`AbstractStrategy`/`Briefing`/`Custom`), `SignalDataService`,
  `OpenAiSignalSummarizer` (gpt-4o-mini), `CronEvaluator`, `SignalsTick` cmd,
  `RunSignalJob` (creates run → runs strategy → advances `next_run_at` → delivers via
  `SignalRunCompleted` notification on `['database','broadcast']`). `action_config.tool_plan`
  is ALREADY executed by `AbstractStrategy`. DB currently has 4 active signals, all due.
- **The one dormant line:** `bootstrap/app.php:30` — `$schedule->command('signals:tick')…`
  is commented. Queue = redis, no worker running, `OPENAI_API_KEY` set.
- **chat.360ai ↔ Laravel channel = MCP only.** chat calls Laravel tools through the MCP
  server named `360ai`, authenticated with the user's OIDC access token
  (`{{LIBRECHAT_OPENID_ACCESS_TOKEN}}`) — see `api/server/services/Onboarding.js`
  (`callOnboardingTool`). The `internal` sanctum-session API is NOT reachable from
  chat.360ai (no browser session). Therefore the chat surface MUST source data via a new
  **MCP tool**, not the internal REST API.
- **chat.360ai realtime = SSE, job-scoped only.** No per-user push channel exists. A
  server-originated message can be persisted via `saveMessage` (upsert on `messageId`+`user`;
  precedent: error paths use `sender:'System'` with no user turn) but the client only
  observes it on refetch. So delivery is **persist-then-refetch**, not true push.

## 3. Goals (this sub-project)

1. Make the Laravel Signals engine actually run (enable cadence + worker).
2. Expose the authenticated user's recent signal runs to chat.360ai via a new read-only MCP tool.
3. Deliver each new successful run as a digest message in the user's dedicated "Signals"
   conversation in chat.360ai, idempotently.
4. Render the digest (markdown) in the feed; forward-compatible marker for a richer card later.

## 4. Non-goals (deferred)

- True push / a per-user WebSocket or SSE notification channel (separate infra project).
- Email/Slack delivery channels (post-v1 per original spec).
- Creating/editing Signals from inside chat.360ai (the `propose_signal` create flow stays in
  agent.360ai for now; chat is read/consume-only in v1).
- M2/M3 signal types (external events, Crustdata) — out of scope.
- Rich result-card rendering of digest payloads (MVP renders summary markdown; marker reserved).

## 5. Architecture

```
 ┌──────────── Laravel (360ai) ────────────┐        ┌──────── chat.360ai (this repo) ────────┐
 │ signals:tick (cron) ──▶ RunSignalJob     │        │                                         │
 │   strategy → tools → OpenAI summariser   │        │  GET /api/signals/sync  (auth: req.user)│
 │   → signal_runs.summary  (+ notification)│        │     │                                   │
 │                                          │  MCP   │     ▼                                   │
 │ Mcp\Tools\GetSignalRuns  ◀──── Bearer ───┼────────┼─◀ callSignalTool(user,'get_signal_runs')│
 │   AgentContext::fromRequest → user/client│ token  │     │                                   │
 │   returns {signals[], recent_runs[]}     │        │     ▼                                   │
 └──────────────────────────────────────────┘        │  SignalsDelivery.deliverNew(user):       │
                                                     │    resolve/create "Signals" conversation │
                                                     │    for each undelivered successful run:  │
                                                     │      saveMessage(role:assistant,         │
                                                     │        text: summary + marker)           │
                                                     │    mark run delivered (dedup set)        │
                                                     │  client refetches messages → renders     │
                                                     └─────────────────────────────────────────┘
```

### 5.1 Transport decision: MCP-tool poll (chosen)
Rationale: it is the **only** chat→Laravel channel that works today (proven by onboarding);
reuses the user's OIDC token (no new cross-repo identity mapping); requires no new auth
surface; chat.360ai owns its Mongo + conversation + `saveMessage`. Trade-off: poll cadence,
not instant push — acceptable for a periodic digest. Rejected alternatives:
- Laravel→chat webhook: requires solving "Laravel authenticates to chat + resolves chat user"
  (net-new cross-repo identity) — high risk, low reuse.
- Shared-Mongo writes from Laravel: couples repos to LibreChat's schema — brittle.
- New per-user SSE/WS in chat: biggest build, separate infra project (deferred non-goal).

### 5.2 Destination decision: dedicated "Signals" conversation per user
A single, auto-created conversation titled "Signals" (with a stable conversationId resolved
per user and cached on the user document) holds all digests. Rationale: keeps digests out of
working conversations; one browsable history; enables a future left-rail unread badge; one
clean place to apply the digest marker/renderer.

### 5.3 Idempotency
Track delivered run IDs per user in a `deliveredSignalRunIds: string[]` field on the user
document (bounded, newest-first, capped at e.g. 200). `deliverNew` fetches recent runs,
filters out already-delivered ids, saves one message per new run, then appends the ids.
Capping prevents unbounded growth.

### 5.4 Marker (forward-compatible, zero MVP cost)
Each digest message text ends with a trailing line:
`<!--signal-digest:RUN_ID-->`
MVP: strip it before markdown render (mirrors `stripOnboardingMarkers`). Later: a resolver
can read it to render a rich card from the run payload. Nothing depends on it today.

## 6. Data / contract

### 6.1 New MCP tool `get_signal_runs` (Laravel)
- Read-only, idempotent (`#[IsReadOnly]` `#[IsIdempotent]`), name `get_signal_runs`,
  empty schema (like `get_onboarding`).
- `AgentContext::fromRequest($request)` → user + client.
- Returns JSON:
  ```json
  {
    "signals": [{ "id","name","type","is_active","next_run_at","last_run_at" }],
    "runs": [{ "id","signal_id","signal_name","status","summary","created_at" }]
  }
  ```
  `runs` = the user's (and their subscriptions') most recent N (e.g. 25) runs across their
  signals, `status` in `['succeeded','failed','no_change']`, `summary` included for
  `succeeded`/`failed`. Ordered `latest-first`. Only runs newer than a notional horizon
  (e.g. created within 30d) to bound the set the client must dedup against.

### 6.2 chat.360ai service `SignalsDelivery` (`packages/api/src/signals/`)
- `getRecentSignalRuns(user): Promise<SignalRunDto[]>` — thin wrapper over
  `callSignalTool` (clone of `callOnboardingTool` calling `get_signal_runs`).
- `resolveSignalsConversation(user): Promise<string>` — find/create the user's Signals
  conversation (UUID); cache its id on the user doc (`signalsConversationId`).
- `deliverNewSignalRuns(user): Promise<{ delivered: number }>` — orchestrate: fetch → filter
  undelivered → saveMessage each → update `deliveredSignalRunIds`.
- `formatDigest(run): { text, messageId }` — `text = run.summary + "\n\n<!--signal-digest:"+run.id+"-->"`,
  deterministic `messageId` from a namespace + runId (so re-runs are upsert-idempotent).
- No `any`. Shared DTOs in `packages/data-provider`.

### 6.3 HTTP endpoint `GET /api/signals/sync` (chat.360ai, `/api` thin JS)
- Auth = `requireJwtAuth` (mirrors onboarding/acumen endpoints).
- Calls `deliverNewSignalRuns(req.user)`; returns `{ delivered }`. Errors → `{ delivered: 0 }`
  (never breaks the client).

### 6.4 Client
- A `useSignalsSync()` hook calls `GET /api/signals/sync` on an interval + on window focus
  when the app is open, then invalidates the messages query for the Signals conversation if
  it's active (or the conversation list). Lightweight; failures silent.
- `stripOnboardingMarkers` extended (or a sibling `stripSignalMarkers`) to also drop
  `<!--signal-digest:…-->` before markdown render (mirrors existing precedent).

## 8. Tests

- **L2 (Pest):** `GetSignalRuns` returns the user's runs, excludes other users' runs, respects
  subscriptions, caps count, redacts empty summaries.
- **C2 (Jest):** `formatDigest` marker + deterministic id; `deliverNewSignalRuns` dedups via
  `deliveredSignalRunIds`, creates conversation once, saves N messages for N new runs, caps
  the dedup set, swallows fetch errors → `{delivered:0}`.
- **C3:** endpoint auth + returns `{delivered}` + error-safe.
- **C4:** marker stripped from rendered text.
- No automated test covers live prompt/forward behavior — human verifies end-to-end by
  logging into chat.360ai.test after a `signals:tick` run.

## 9. Risks & mitigations
- **Worker/scheduler not running in dev** → enabling the cron is inert without
  `schedule:work`/`queue:work`. Document the run commands; verify manually before declaring done.
- **OpenAI spend** → gpt-4o-mini, read-only tools, per-signal cadence (not every minute).
  Bounded.
- **Poll cost** → interval ≥ a few minutes + on-focus; silent failures; small payload.
- **Conversation proliferation** → one per user, cached on user doc; never re-created.
- **Idempotency gap** → deterministic `messageId` per runId (upsert safe) + deliveredRunId set.

## 10. Out of scope / future
- Per-user push (SSE/WS) channel for instant delivery.
- `propose_signal` create-from-chat.
- Rich card rendering from `payload` (marker reserved for this).
- Left-rail unread badge.
